Why I Still Write Vanilla
HTML/CSS/JS in 2025

Every new project spawns a new framework. npm install gets heavier. The web gets slower. I keep asking: what exactly are we abstracting away, and at what cost?

Umakant Kunal
MSc Computer Science

The first time I opened a freshly scaffolded Next.js project, I stared at the directory tree for a good five minutes trying to locate where the actual HTML was. It was not there — not in any form I recognised. There was a _document.tsx, a _app.tsx, a pages folder, a public folder, a styles folder, and 847 packages already sitting in node_modules before I had written a single line of my own code. 847 packages. For a web page.

I am not here to tell you React is bad. It is not. I use it when it makes sense. But there is a version of this story — and I think it is the dominant version right now — where developers reach for a framework not because the problem demands it, but because reaching for a framework is simply what you do. It is the default reflex. The path of least resistance. And that reflex is quietly eroding something important.

THE FRAMEWORK MONOCULTURE

Walk into any web development job interview in 2025 and the first technical question is almost certainly about React hooks, the Vue reactivity system, or how Next.js handles server-side rendering. Rarely will you be asked how the browser's event loop works. Almost never will you be asked to explain the CSS cascade from first principles, or to describe what actually happens when you call document.createElement. The industry has quietly decided that these things are implementation details — below the abstraction layer, therefore not worth your mental overhead.

This is a problem. Not because frameworks are wrong, but because the abstraction has become so thick that many working developers cannot see through it anymore. They know how to wire up a useState hook but cannot explain what triggers a reflow in the DOM. They know how to configure Tailwind but have never thought carefully about the specificity rules that Tailwind is working around. The foundation has been obscured by the scaffolding placed on top of it.

"Simplicity is a great virtue but it requires hard work to achieve it and education to appreciate it. And to make matters worse: complexity sells better." — Edsger W. Dijkstra

Dijkstra wrote this in 1984. He was talking about software engineering in general, but the sentence lands with particular force when you look at the modern JavaScript ecosystem. Complexity sells better. A framework with a thousand features, a CLI that generates boilerplate, a plugin system for the plugin system — these things look impressive. They look like productivity. Sometimes they are. But often they are complexity renting itself out as convenience.

WHAT ABSTRACTIONS HIDE

Here is a concrete example. In React, you manage side effects with useEffect. You pass a dependency array and React calls your function when those dependencies change. This is a genuinely useful pattern. But lurking beneath it is a mechanism that many React developers have never confronted directly: the browser's own event-driven architecture, the microtask queue, the distinction between painting a frame and committing to the DOM. When your useEffect produces a flicker or runs one time too many, you are not debugging React — you are debugging timing in the browser's rendering pipeline, whether you know it or not. If you do not know it, you are flying blind.

In vanilla JS, you cannot avoid these things. When you attach a scroll listener to window and notice your page stuttering, you are forced to learn about passive event listeners and compositor threads. When your CSS animation jitters, you end up reading about will-change and GPU layer promotion. When you try to measure an element before the browser has painted, you learn about layout thrashing and requestAnimationFrame. None of this knowledge is optional. It is right there, in your face, demanding to be understood.

The DOM API is not pretty. It is verbose, inconsistent in places, and carries thirty years of backward-compatibility baggage. But it is also the actual interface between your code and the pixels on screen. Every framework is just a translation layer sitting on top of it. Understanding the translation target makes you better at using the translator.

PERFORMANCE IS NOT FREE

There is a persistent myth in web development that modern frameworks are fast by default — that the optimisation work has been done for you, and you simply reap the benefits. This was never entirely true, and it becomes less true as applications grow. Virtual DOM diffing is not free. JavaScript bundle parsing is not free. Server components, hydration, concurrent rendering — these are solutions to performance problems that, in many cases, would not exist if the application had been built more simply in the first place.

Consider what is trivial in vanilla JS but routinely over-engineered in framework-land. You want to toggle a class on a button click: two lines of vanilla JS, or a state variable, a re-render cycle, and a conditional class binding in React. You want to animate an element in and out of view: a CSS transition and a class toggle, or an animation library with its own virtual DOM, its own reconciler, its own bundle weight. You want to lazy-load an image: the loading="lazy" attribute, or a third-party component that wraps the native browser behaviour and adds 12KB to your bundle.

"Premature optimization is the root of all evil (or at least most of it) in programming." — Donald Knuth, Computer Programming as an Art (1974)

Knuth's point is usually invoked to argue against micro-optimising too early. But the flip side is also true: premature abstraction is a form of premature optimisation for developer experience — and it has the same failure mode. You pay the complexity cost upfront, before you know whether the abstraction was the right one. A page that ships 400KB of JavaScript to render a blog post is not fast. No amount of code-splitting will make it as fast as a page that ships 8KB of semantic HTML.

DEPENDENCY HELL AND THE ILLUSION OF LEVERAGE

In early 2022, a package called colors.js was deliberately corrupted by its maintainer, breaking thousands of downstream projects. In 2016, the removal of a package called left-pad — eleven lines of code — took down Babel, React, and dozens of major applications. These are not edge cases. They are symptoms of an ecosystem that has mistaken dependency depth for engineering maturity.

The Unix philosophy, articulated by Doug McIlroy in the early days of Bell Labs, offered a different vision: write programs that do one thing and do it well; write programs that work together; write programs that handle text streams, because that is a universal interface. The spirit of this philosophy is not minimalism for its own sake. It is about keeping the surface area of your system small enough to reason about. A node_modules folder with 900 transitive dependencies is not small enough to reason about. It is a cathedral built on sand, with each grain held in place by a package maintainer who might wake up tomorrow and decide they are done.

A vanilla HTML/CSS/JS project has no transitive dependencies. It has no build step, no bundler configuration, no version conflicts, no CVE alerts for packages three layers deep that you have never heard of. It boots in a browser. It will boot in a browser in ten years. It ran in Netscape and it will run in whatever comes after Chrome. That is durability. That is leverage that compounds over time instead of decaying.

WHAT YOU LEARN WITHOUT TRAINING WHEELS

Alan Kay, one of the architects of modern object-oriented programming, once said that the real computer revolution has not happened yet — that we are still largely thinking in terms of the old tools when fundamentally new ways of thinking are available to us. I take a narrower version of that point: the real web development revolution that has happened — the standardisation of HTML5, the maturity of CSS, the ES6+ language features that made JavaScript genuinely pleasant to write — is underappreciated because it happened underneath the framework layer, where most working developers no longer look.

"The computer revolution hasn't happened yet." — Alan Kay

CSS Grid and Flexbox are extraordinary layout systems. They make things possible in fifteen lines of CSS that would have required JavaScript hacks and absolute positioning ten years ago. CSS custom properties are a proper variable system. IntersectionObserver, ResizeObserver, MutationObserver — these are powerful, efficient browser APIs that solve real problems without a dependency in sight. fetch, async/await, the module system, localStorage, the History API, Web Workers — the platform has grown up, quietly, while the ecosystem was busy building tools to abstract it away.

When you build without a framework, you have no choice but to learn these things. You write a toggle and you learn event delegation. You build a scroll animation and you learn about viewport coordinates and getBoundingClientRect. You add a theme switcher and you learn about CSS custom properties and localStorage. Every problem you solve deposits knowledge directly into your understanding of how the web actually works — not how one framework's model of the web works, but the real thing.

FUNDAMENTALS AS THE FOUNDATION OF EXPERTISE

I have noticed a pattern in the developers I find most impressive. They are fluent in frameworks — they can pick up a new one in days, not weeks. They do this not because they keep up with every release, but because they understand what every framework is fundamentally trying to do. They understand reactivity, so they understand Vue. They understand the reconciliation problem, so they understand why React's virtual DOM exists. They understand the server/client boundary, so Next.js's mental model clicks immediately. Frameworks become easy when you understand the problems they were built to solve.

The developers I find least impressive are sometimes very fast in their chosen framework — but helpless outside it. Ask them to debug a layout without DevTools. Ask them to write a debounce function without lodash. Ask them why a particular element is not getting the CSS property they set. Watch the framework's abstraction dissolve, and see what is left underneath. Often: not much. This is not a character flaw. It is what happens when you learn tooling before you learn craft.

The best analogy I know is mathematics education. You can teach a student to use a calculator from day one and they will be able to produce correct numerical outputs very quickly. Or you can teach them arithmetic, algebra, and the underlying structure of numbers, and they will eventually be able to do things with mathematics that the calculator-first student never will — because they understand what the calculator is doing. Frameworks are calculators. HTML, CSS, and JavaScript are arithmetic. You need both, but in that order.

A PERSONAL STATEMENT

This portfolio — the one you are reading right now — is built entirely in vanilla HTML, CSS, and JavaScript. No React. No build step. No bundler. No dependencies at all. Every animation, every layout, every interaction is hand-written using nothing but the web platform itself.

I made this choice deliberately, as a statement. Not because I am opposed to frameworks — I use React professionally and I have genuine respect for what the teams behind Next.js, Vue, and Svelte have built. But I wanted to prove something to myself: that I understand the substrate, not just the abstraction. That I can reason about the browser directly. That I do not need a compiler between me and my work.

There is something clarifying about that constraint. When there is no framework to reach for, you think harder about what you actually need. You write less code. You make fewer assumptions. You end up with a codebase that loads in a single HTTP request, runs on any device with a browser, and has exactly zero vulnerability surface from transitive dependencies. The starfield behind this text? A hundred lines of vanilla canvas API. The read progress bar at the top of the page? Six lines. The whole site: under 1,500 lines of code total, zero build steps, zero dependencies.

I am an MSc AI student. I spend most of my days thinking about neural architectures, loss landscapes, and the mathematics of learning. But when I sit down to build something for the web, I find myself returning to the same instinct: understand the system you are working with, all the way down. Not because it is efficient — sometimes it is slower. But because the knowledge compounds. Because the next time I pick up a framework, I will know what it is doing and why. Because the difference between a craftsman and a tool operator is not which tools they use — it is whether they understand the tools, or are merely used by them.

Write vanilla once. Really write it. Fight with the DOM, figure out the event bubbling, wrestle with CSS specificity until you understand why it works the way it does. Then use whatever framework makes you productive. You will be better at it. I promise.
