How the Internet Actually Works —
From Your Keyboard to a Server on
the Other Side of the World

You type a URL and press Enter. In less than a second, text arrives on your screen from a computer possibly thousands of kilometres away. This is so routine that we forget how extraordinary it is. Every single step involves elegant engineering solutions to genuinely hard problems. Let's trace the whole journey.

Umakant Kunal
MSc Computer Science

Start with the miracle, because it really is one. Right now, hundreds of millions of people are doing exactly the same thing — typing an address into a browser, pressing Enter, and receiving a response from a machine they have never touched, operated by a company they will never meet, routed through infrastructure owned by dozens of different organisations across multiple countries, all within the time it takes to blink. No single engineer designed this. No single company controls it. It emerged from decades of protocol design, competitive pressure, academic collaboration, and sheer accumulated engineering effort. It is, without exaggeration, the most complex human-built system that has ever existed — and it works reliably enough that we treat it as a utility, like water from a tap.

What follows is a trace of every major layer of that journey, from the moment your finger lifts off the Enter key to the moment pixels appear on your screen. We will not skip the hard parts. The hard parts are where the interesting engineering lives.

DNS — THE PHONEBOOK

Your browser does not know where google.com lives. No one gave it a map. What it has is a name — a human-readable string that means nothing to a router. Routers speak in IP addresses: numbers like 142.250.180.46 that identify a specific machine on the network. The Domain Name System is the global infrastructure that translates one into the other. Without DNS, you would have to memorise IP addresses for every website you visit. With DNS, you type a name and the system does the lookup for you.

The resolution process involves several layers, each with its own cache. Your browser checks its own DNS cache first — modern browsers cache recent lookups for a few minutes. If the answer is not there, it asks the operating system, which maintains its own cache and also checks the local hosts file. If neither knows the answer, the request goes to a recursive resolver — typically your ISP's DNS server, or a public resolver like 1.1.1.1 (Cloudflare) or 8.8.8.8 (Google). The recursive resolver does the heavy lifting: it queries the root nameservers (there are 13 logical root servers, operated by organisations like ICANN, NASA, and Verisign), which respond with the address of the TLD nameserver responsible for .com, .org, or whatever top-level domain you're querying. The TLD nameserver then points to the authoritative nameserver for the specific domain — the server that holds the actual DNS records. That server returns the IP address, and the answer propagates back through the chain to your browser.

Each record has a TTL — time to live — that tells caches how long to hold the answer before discarding it and asking again. When DNS is slow, everything is slow. A lookup that takes 200ms adds 200ms to every page load for a new domain. This is why DNS performance matters, why large companies run their own authoritative DNS infrastructure, and why browser-side caching is so aggressive. DNS over HTTPS (DoH) encrypts DNS queries inside HTTPS, preventing your ISP from seeing which domains you're looking up — a meaningful privacy improvement that is increasingly the default in modern browsers.

"The internet is not one thing. It's a collection of things — of independently operated networks that have agreed to interconnect and exchange traffic according to common protocols." — Vint Cerf, co-creator of TCP/IP, often called the Father of the Internet

TCP/IP — THE ENVELOPE

Now your browser has an IP address. It needs to send data to that address across a network that has no guaranteed path between any two points, no central dispatcher, and no guarantee that any given link is even up. The solution is packet switching: data is broken into small chunks called packets, each labelled with a source and destination IP address, and each routed independently through the network. Different packets in the same request can take different physical paths and arrive out of order. The internet does not guarantee delivery — it just does its best.

IP (Internet Protocol) handles the addressing and routing. Every packet has a header containing source IP, destination IP, TTL (decremented at each hop — a packet that circulates forever gets dropped), and a protocol field indicating what's inside. IP is connectionless and stateless: each packet is routed independently, with no memory of previous packets.

TCP (Transmission Control Protocol) lives on top of IP and provides what IP does not: reliability, ordering, and error detection. Before any data can flow, TCP establishes a connection via the three-way handshake. Your machine sends a SYN packet to the server, saying "I want to connect." The server replies with a SYN-ACK, acknowledging the request and sending its own synchronisation sequence. Your machine replies with an ACK, and the connection is live. From this point, TCP guarantees that packets arrive in order, retransmits anything that gets lost, and adjusts its transmission rate based on network congestion. Every byte sent gets an acknowledgement; anything unacknowledged gets resent.

UDP (User Datagram Protocol) trades all of that reliability for speed. UDP has no handshake, no ordering guarantees, no retransmission. A packet either arrives or it doesn't, and neither side particularly cares about the ones that didn't. This sounds irresponsible until you consider the use cases: video calls, online games, and DNS queries all benefit enormously from low latency. In a video call, a dropped packet is better replayed as silence or a blurry frame than delayed while the system waits for a retransmit. DNS queries are tiny and idempotent — if the answer doesn't arrive, just ask again. UDP is the right tool for these jobs.

TCP's congestion control is one of the internet's unsung heroes. Without it, the network would routinely collapse into congestion death spirals. Algorithms like CUBIC and BBR continuously probe available bandwidth, increasing send rates when the network is clear and backing off aggressively when packets start getting dropped or delayed. The internet you know — where a hundred people can stream video simultaneously on the same ISP link — exists partly because TCP is designed to be polite about sharing bandwidth it doesn't own.

BGP — THE POSTAL SERVICE

Your packet has a destination IP and is riding inside TCP. Now it needs to physically travel across the internet — through routers owned by your ISP, other ISPs, backbone providers, and eventually the network that hosts the server you're talking to. Border Gateway Protocol (BGP) is the system that tells each router how to reach every other network on the internet. It is, in a very real sense, what makes the internet a single connected system rather than a collection of isolated local networks.

The internet is organised into Autonomous Systems (ASes) — large networks operated by a single administrative entity, such as an ISP, a university, or a large company. Each AS gets a unique number (an ASN) and is responsible for routing within its own network. BGP is the protocol by which ASes announce to each other which IP prefixes (ranges of addresses) they can reach, and by which they propagate that information to the rest of the internet. When Cloudflare announces 104.16.0.0/12, it is telling every other AS: "Send packets for these addresses to us."

BGP is both beautiful and terrifying. Beautiful because it is a genuinely distributed consensus protocol — there is no central authority, no master routing table, no single point of failure. The entire routing infrastructure of the internet emerges from thousands of bilateral agreements between autonomous systems, each sharing what it knows. Terrifying because those agreements are largely based on trust, enforced by business relationships and reputation rather than cryptographic verification. Any AS can announce that it owns any IP prefix, and for a few minutes — sometimes longer — the rest of the internet will believe it.

This is not hypothetical. In 2008, Pakistan Telecom accidentally (or otherwise) announced ownership of YouTube's IP prefixes to its upstream provider, which propagated the announcement globally. YouTube vanished from the internet for roughly two hours before the error was identified and corrected. Similar incidents happen every year: a misconfigured router announces wrong routes, traffic gets redirected through networks it was never supposed to traverse, and the internet silently reroutes around the problem — or doesn't. BGPsec and RPKI (Resource Public Key Infrastructure) are efforts to cryptographically verify route announcements, but adoption is slow and the internet's routing infrastructure remains fundamentally designed for cooperation, not adversarial conditions.

"The internet was designed to be resilient to nuclear attack, but it was not designed to be resilient to a malicious participant who has been given a seat at the table." — Werner Vogels, CTO of Amazon Web Services, on infrastructure trust assumptions

TLS — THE SEALED ENVELOPE

Your packet can now navigate from your machine to the server. But the path crosses networks you do not own, through routers you have never audited, over cables that someone else controls. Without encryption, every intermediary can read every byte. Transport Layer Security (TLS) — the protocol behind the padlock icon in your browser — solves this by establishing an encrypted tunnel between your machine and the server before any application data is sent.

The TLS handshake runs on top of TCP and involves several steps. First, your browser sends a ClientHello message listing the TLS version it supports, a list of cipher suites it can use (combinations of key exchange, authentication, and encryption algorithms), and a random nonce. The server replies with a ServerHello, choosing a cipher suite from the list, and sends its X.509 certificate — a document containing the server's public key, its domain name, and a digital signature from a Certificate Authority (CA) that vouches for the key's authenticity.

Your browser verifies the certificate: is it signed by a CA it trusts? Is the domain name in the certificate the one you requested? Has the certificate been revoked? Assuming all checks pass, the two sides perform a key exchange. Modern TLS uses Elliptic Curve Diffie-Hellman (ECDH), which lets both sides independently compute the same shared secret without ever sending it across the network. From this shared secret, both sides derive symmetric session keys used for the rest of the connection. All data from this point is encrypted with AES-GCM — fast, authenticated symmetric encryption that prevents both eavesdropping and tampering.

Certificate transparency is a relatively recent addition to the ecosystem: all issued certificates are logged in public, append-only ledgers, making it possible to detect a CA that has issued a fraudulent certificate for your domain. Browsers increasingly require certificates to be logged before they will trust them. The system is not perfect — CAs have been compromised before — but it has significantly raised the cost of undetected certificate fraud.

HTTP — THE LETTER

Inside the encrypted TLS tunnel, your browser sends an HTTP request. HyperText Transfer Protocol is the application-layer language that web clients and servers speak. An HTTP request consists of a method (GET, POST, PUT, DELETE), a path (/search?q=hello), HTTP headers (metadata: Accept-Encoding, User-Agent, Cookie, Authorization), and optionally a request body.

HTTP/1.1, standardised in 1997, had a fundamental limitation: one request per TCP connection at a time. A page loading 50 resources needed to either wait for each one sequentially or open many parallel TCP connections (browsers typically opened 6 per domain). Head-of-line blocking meant that a slow resource held up everything behind it in the queue.

HTTP/2, released in 2015, addressed this with multiplexing: multiple requests and responses can be interleaved over a single TCP connection, labelled with stream identifiers so both sides know which bytes belong to which request. Header compression (HPACK) reduced the overhead of sending the same headers with every request. Server push allowed the server to proactively send resources the client would need before it had even asked for them. HTTP/2 was a genuine step forward.

HTTP/3 goes further by abandoning TCP entirely. Built on QUIC — a new transport protocol running over UDP — HTTP/3 eliminates TCP's head-of-line blocking at the transport layer. In HTTP/2, a lost TCP packet stalls all streams on that connection until the packet is retransmitted. In QUIC, each stream is independent: a lost packet only blocks the stream it belongs to. QUIC also builds TLS into the protocol from the start, reducing the number of round trips needed to establish a connection. For mobile users switching between networks — from Wi-Fi to cellular — QUIC's connection migration means the connection survives the network change without needing a new handshake.

HTTP status codes tell you what the server actually thought of your request. 2xx means success (200 OK, 201 Created). 3xx means redirection (301 Moved Permanently, 304 Not Modified — meaning the cached version is still good). 4xx means client error (400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found). 5xx means the server itself failed (500 Internal Server Error, 503 Service Unavailable). When you get a 503, the server received your request fine — it just can't handle it right now. BGP is working, TLS is working, TCP is working, HTTP is working. The application is broken.

THE BROWSER

Bytes have arrived. They represent an HTML document — a text file with tags describing the structure and content of a page. What happens next is a pipeline called the critical rendering path, and understanding it is what separates developers who write fast pages from developers who wonder why their pages are slow.

The browser parses HTML top-to-bottom, building the DOM (Document Object Model) — a tree of nodes representing every element on the page. When the parser encounters a <link> tag pointing to a CSS file, it must fetch that file and parse it into the CSSOM (CSS Object Model) before it can continue rendering — CSS is render-blocking. When it encounters a <script> tag without async or defer, it must fetch, parse, and execute that JavaScript before continuing — scripts can modify the DOM and must run in order. This is why the position of <script> tags matters enormously for page performance.

With the DOM and CSSOM built, the browser combines them into a render tree — a tree of every visible element with its computed styles. It then runs layout (also called reflow): calculating the exact pixel dimensions and position of every element. After layout comes paint: filling in pixels with colours, text, images, borders. Finally, composite: assembling the painted layers in the correct order, handling opacity, transforms, and z-indices.

Time to First Byte (TTFB) measures how long until the first byte of the response arrives. Time to Interactive (TTI) measures how long until the page is actually usable — until JavaScript has finished executing and event handlers are attached. These can differ by seconds on a JavaScript-heavy page that downloads fast but executes slowly. Modern performance measurement focuses increasingly on Core Web Vitals: Largest Contentful Paint (how long until the main content appears), Cumulative Layout Shift (how much the layout jumps around as it loads), and Interaction to Next Paint (how responsive the page feels to clicks).

The JavaScript engine — V8 in Chrome and Node.js, SpiderMonkey in Firefox, JavaScriptCore in Safari — parses the JavaScript source, compiles it to bytecode, and then uses just-in-time (JIT) compilation to convert hot code paths to native machine code at runtime. Modern JS engines are marvels of optimisation: they inline functions, eliminate dead code, and generate specialised machine code based on the actual types they observe at runtime.

"The web is more a social creation than a technical one. I designed it for a social effect — to help people work together — and not as a technical toy." — Tim Berners-Lee, inventor of the World Wide Web, Weaving the Web

CDNs AND THE EDGE

There is a hard physical limit on how fast the internet can be: the speed of light. An optical fibre carrying a signal from London to Sydney covers roughly 17,000 kilometres. Light in glass travels at about two-thirds of its speed in vacuum — approximately 200,000 km/s. The theoretical minimum round-trip time is around 170 milliseconds, and in practice it is higher because the path is not a straight line and packets make multiple hops. No amount of software optimisation can overcome this. The only solution is to move the data closer to the user.

Content Delivery Networks do exactly this. Cloudflare, Fastly, and Akamai operate hundreds of Points of Presence (PoPs) — data centres distributed across the globe. When you request a static asset — an image, a CSS file, a JavaScript bundle — the CDN serves it from the PoP nearest to you rather than from the origin server. A user in Mumbai requesting a file stored in Virginia might instead receive it from a Cloudflare PoP in Mumbai, with a round-trip time of 5 milliseconds instead of 200.

Edge computing extends this further. Instead of just caching static files, edge platforms like Cloudflare Workers and Fastly Compute@Edge allow you to run code — actual application logic — at the edge. A personalisation layer, an A/B test, an authentication check: all of these can execute at the PoP nearest the user, adding minimal latency to the response. The architecture is a reversal of the traditional model: instead of a central origin handling everything, computation is distributed to wherever the user is.

CDNs also provide DDoS protection, SSL/TLS termination at the edge, HTTP caching, and load balancing. For most web applications, traffic never reaches the origin server for the vast majority of requests — it is served entirely from edge cache. The origin handles only cache misses and dynamic, uncacheable requests.

When I trace this journey end to end — DNS, TCP/IP, BGP, TLS, HTTP, browser rendering, CDN — what strikes me is not any single clever idea but the sheer accretion of layers, each built by different people at different times to solve different problems, all somehow interoperating. These systems were not designed together. Many were designed in opposition: TCP was designed before TLS existed, HTTP/1.1 before HTTP/2's multiplexing was imagined, BGP before anyone seriously considered adversarial route announcements. Each protocol is a snapshot of the problems that seemed most important at the time, with workarounds bolted on as new problems emerged.

And yet it works. Every time you press Enter, this entire chain executes — across continents, across organisations, across protocols designed by people who will never meet each other — and delivers a response in milliseconds. We have built an infrastructure layer so reliable that we treat failures as aberrations rather than the norm. We trust it with banking, with healthcare, with the communication that binds people separated by oceans. We barely think about it.

That invisibility is the highest compliment infrastructure can receive. The engineers who built this were not trying to make something you would notice. They were trying to make something that would disappear — that would be so dependable, so fast, so ubiquitous that you would stop thinking about it entirely. By that measure, they succeeded beyond anything they could have imagined in the 1970s when the first packets were exchanged. The internet is not finished — HTTP/3, QUIC, encrypted DNS, BGP security, and whatever comes next are all still in motion. But the bones of it are extraordinary. It deserves, occasionally, to be seen.
